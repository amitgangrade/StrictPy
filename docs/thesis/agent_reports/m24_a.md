## What the scheduler does

`examples/job_scheduler.spy` builds a tiny but realistic background
job scheduler that combines four Phase 3a modules in one program.
Six hardcoded shell jobs are pushed onto a `queue.PriorityQueue` keyed
by priority (lower runs first).  A pool of three worker threads
(`from threading import Thread`) each loops: `threading.semaphore_acquire`
(block until work is available), pop the next job off the PQ, invoke
the command via `subprocess.run`, capture the exit code.  On
success, the worker records `(job-id, exit_code, datetime.now())` into
shared parallel `List[i32]/List[i64]` slots under a
`threading.Lock`; on failure, it bumps the retry counter (under a
second `state_lock`) and either re-queues the job with priority
bumped by `10 * retry_count` and a `datetime.add_seconds` backoff
calculation, or — if `retry_max` is exhausted — records the failure
and decrements the global pending counter.  Main thread polls the
pending counter until 0, then sends one poison-pill ID per worker
(priority `1e9`, jid `-1`) and joins.  Four jobs succeed (`alpha`,
`bravo`, `charlie`, `delta`), two fail and exhaust their retry
budgets (`fail-eager` with retry_max=2 logs 3 attempts;
`fail-late` with retry_max=1 logs 2 attempts).  The headline
summary line is `success=4` / `failed=2`, asserted by the integration
test.

## Bugs found

**Zero.**  Every probe — including the deliberately racy ones
(probe 7's concurrent push/pop, probe 4's kill-from-another-thread)
— ran clean on the first compile.

This is the second consecutive stress round with no new bugs (M18
also reported zero against the M13–M17 surface).  The hypothesis from
M23 P3a-A/B/C — that the stdlib-module-table infrastructure has
hardened into the most stable surface in the VM — holds under
combination-stress, not just per-module unit tests.

The M23 P3a-C agent worried specifically about:

* `subprocess.wait` from a worker thread deadlocking — probe 2 directly
  drives this with 4 workers each spawn+wait, and they all return in
  <100ms total.  No deadlock observed.
* `threading.Semaphore` missed wakeups — probe 6 directly drives this
  ("blocked acquirer waits for delayed release").  Three workers
  blocked-on-acquire wake every time the main thread releases three
  permits.  No wakeup loss observed across many test invocations.
* `queue.PriorityQueue.pq_push_i64` thread-safety — probe 7 drives
  3 workers all pushing+popping concurrently for 40 total ops, with a
  hard cap of 1000 iterations each.  No panics, no missing items,
  final queue state is empty.

## Workarounds reached for (and what they imply)

Three minor syntactic workarounds, none indicating a bug:

1. **Multi-line `fn` signatures and multi-line call arguments are not
   accepted.**  My first cut of `worker_body(...)` with its 12
   parameters was a multi-line def
   (`fn worker_body(\n    worker_id: i32,\n    ...\n) -> None:`).
   The parser rejected the close-paren on its own line with
   `expected identifier, found RParen`.  Fix: collapse to one long
   line.  Likewise the three `Thread(fn() -> None: worker_body(...))`
   sites — each 13-argument call had to land on one line.  This is
   the same lexer-line-continuation issue tracked as BUG-028
   (the *only* open bug as of M23).  Cosmetic; documented in the
   scheduler's comment block.

2. **`as` is not the cast operator.**  My first cut used Rust's
   `(rc as i64)` / `(rc as f64)` syntax inside `add_seconds` and
   `10.0 * (rc as f64)`.  StrictPy uses constructor-style casts:
   `i64(rc)` / `f64(rc)`.  Rewrote — works.  The `as` keyword is
   spoken-for by `try ... except IOError as e:`.

3. **Per-expression nullable narrowing forces a "narrow positive"
   form on `try_wait` results.**  My first cut of probe 3 wrote:

   ```
   maybe: i32? = subprocess.try_wait(h)
   if maybe is none:
       ...
   else:
       final_code = maybe   # narrowing not in scope here
   ```

   The `else` branch of `is none` doesn't propagate narrowing in v0.2.
   Re-spelling as `if maybe is not none: final_code = maybe` works
   immediately.  Same pattern that `btree.spy` reaches for
   (`unwrap_node` helper); not new.

None of these are bugs — they're known v0.2 limits documented in the
spec and in the SHARED_BRIEF "known v0.2 limits" list.

## Confirmed v0.2 limits I respected (didn't try to push past)

* **Module-level statements with side effects** can't run in v0.2 —
  all scheduler state is built inside `main()` and passed via
  primitive-handle (`i64`) into worker closures.
* **`subprocess.kill` on Windows** sends `TerminateProcess(1)` — the
  resulting exit code is `1`, not `-9` (Unix's SIGKILL).  Probe 4
  asserts only that the code is non-zero, so it runs portably.
* **`threading.Lock` is non-reentrant** — every probe acquires +
  releases in strict pair-form, never holds across recursive calls.
  The two distinct locks in the scheduler (`log_lock` vs
  `state_lock`) are taken in a consistent order to avoid
  cross-lock deadlock.
* **`datetime` is integer-second precision** — backoff arithmetic
  uses whole-second offsets only; the scheduler doesn't actually
  *sleep* between retries (it just verifies the `add_seconds` math),
  so the lack of sub-second precision doesn't affect the test.

## Implementation choices

A few non-obvious decisions worth recording:

1. **Two locks, not one.**  Originally I used a single
   `results_lock` covering both the per-job outcome slots and the
   `pending_left` counter.  But the `pending_left` decrement is a
   tight read-modify-write; holding the log-lock across the larger
   outcome-update region was wasteful.  Splitting into
   `log_lock` (around `outcome_code` / `outcome_finish` writes) and
   `state_lock` (around `pending_left` / `retry_count`) cut
   contention and isolated the lock-ordering rule (state_lock
   *never* held while log_lock is held; only one direction needed).

2. **Semaphore-driven worker wake-up, not busy-poll.**  The brief
   explicitly called this out: workers `semaphore_acquire()`
   instead of polling `pq_is_empty()`.  Main thread releases one
   permit per push (initial seed jobs + every retry).  This is the
   canonical producer-consumer pattern and it exercises probe 6's
   "Semaphore as blocking signal" goal in production.

3. **Poison-pill termination, not flag-and-spin.**  Main thread
   pushes `N` poison-id (`-1`) entries with priority `1e9` (always
   last to pop) and releases N permits.  Each worker checks the
   popped jid against `poison_id()` and returns.  This avoids the
   "graceful shutdown while a job is in flight" race that a boolean
   `stop` flag would introduce, and it works cleanly with the
   strict counting semaphore (no need for broadcast).

4. **Retry-count semantics: each attempt increments.**  A job with
   `retry_max=2` will record `retries=3` in its summary row (1
   initial + 2 retries).  The integration test asserts this exact
   value.  Could have been "retries excludes the initial" instead
   — that's a documentation call.

5. **Three workers, not four.**  Four worker threads + one main
   thread = 5 OS threads; on the M23 P3a-C 8-thread Windows CI
   host, this is comfortable headroom.  Three is a more
   conservative pick that still demonstrates contention without
   stressing the host scheduler.

## What this round implies for v0.3

* **Multi-line `fn` signatures** would unlock real Python ergonomics.
  My 12-param `worker_body` is functional on one line but visually
  hostile.  This is a parser-side change only (lexer line
  continuation across `(` / `,` / `)`); same root cause as BUG-028.
* **Nullable narrowing through the `else` of `is none`** would have
  saved a re-spelling step in probe 3.  Per-expression narrowing
  works for the `is not none` case; extending it to the negative
  case would mostly be a typechecker-side mirror.
* **A `with` form for locks** (`with threading.lock_acquire(h): ...`)
  would mechanise the lock-pair discipline.  The M23 P3a-C report
  flagged this as a v0.3 ergonomic upgrade; the scheduler is one
  more data point in its favour (every lock-acquire/release pair
  is repeated 6 times in the scheduler, with no way to forget the
  release on an unexpected raise).

These aren't gaps that *blocked* this round — they're paper cuts that
showed up because the program does enough threading + lock-handling
to make repetition visible.

## Verdict on Phase 3a

Phase 3a is the most mechanically-stable stdlib round so far.  Four
modules + 4 worker threads + a real OS subprocess loop = zero new
bugs found.  The "stdlib-module-table infrastructure absorbs all new
modules without resolver/typecheck/IR changes" thesis from M19 / M20 /
M22 / M23 P3a-A,B,C,D still holds in combination-stress.

The M24 round-wide question was "the combination-stress finds bugs
the per-module unit tests miss".  My slice's answer: **not on the
subprocess + threading + queue + datetime combination, at any rate.**
The three siblings (B/C/D) report separately; the orchestrator's
roll-up will tally.
