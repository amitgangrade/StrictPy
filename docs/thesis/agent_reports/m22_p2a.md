# M22 P2A — `argparse` + `collections` + `csv`

**Brief**: Phase 2's first parallel-agent stdlib round.  Ship three
high-ROI modules on top of M19's stdlib-module-table infrastructure:
`argparse` (so CLI tools stop hand-walking `sys.argv`), `collections`
(Counter + deque, so M10's wordcount stops hand-rolling a freq table),
and `csv` (so M10's `csv_aggregate.spy` machinery becomes a named
stdlib).

**Wall-clock**: ~3 hours (one read-through, three module
registrations, ~450 LOC of native handlers, 18 in-process tests + 8
subprocess tests + 3 example programs + spec).
**Files changed**: 4 source files + 1 spec section + 1 agent report +
3 new examples + 4 new test files.
**ID range used**: 250–280 of the assigned 250–289 block (31/40 slots
used; 9 reserved for v0.3 extensions inside the same modules).
**Tests**: 379 baseline (M21) + **26 new** (18 in-process + 8

_examples`, `parse_examples`, `typecheck_examples`) = **405 passing,
0 failing, 1 ignored**.

## Strategy: ride M19's infrastructure, no new resolver surface

The brief flagged a design fork for `argparse`: a typed `ArgParser`
sealed prelude class (the Pythonic surface) versus a `Dict[str, str]`
"opaque handle" flat API (the v0.2-compatible scope-down).  The
prelude-class route would have meant registering two new sealed
classes (`ArgParser`, `Args`), each with their own `is_native: true`
ClassLayout, method tables, and IR dispatch — but M20c's report had
already flagged stdlib-class registration as **v0.3 work** (the
typed `JsonValue` surface punted for the same reason).  Doing it just
for argparse would be massive yak-shaving 12 weeks before v0.3 lands.

I scoped down to **the Dict-of-strings handle**.  The signature shape:
```
fn new(prog: str) -> Dict[str, str]
fn add_flag(p: Dict[str, str], name: str, default: bool) -> None
fn add_arg(p: Dict[str, str], name: str) -> None
fn add_opt(p: Dict[str, str], name: str, default: str) -> None
fn parse(p: Dict[str, str], argv: List[str]) -> Dict[str, str]
fn get_flag(a: Dict[str, str], name: str) -> bool
fn get_arg(a: Dict[str, str], name: str) -> str
fn get_opt(a: Dict[str, str], name: str) -> str
fn help_text(p: Dict[str, str]) -> str
fn help_requested(argv: List[str]) -> bool
```

The internal storage convention encodes declaration kind in the key
prefix (`flag:NAME`, `opt:NAME`, `arg:NAME`) and uses two reserved
keys (`_prog_`, `_order_`) for program name and positional ordering.
The ordering uses `\u{1F}` (ASCII US separator) as a join character
because comma/space/dot are all common in arg names but US is not.
Defended in `argparse_check_name`.

This let me reuse M7's `Dict[K, V]` machinery end-to-end: no new heap
shape, no new native ID for a fresh "ArgParser handle" type, no new
typecheck path.  The diff is **all in `seed_stdlib_modules` +
`vm/src/builtins.rs`** — zero touch to resolver attr lookup,
typecheck, or IR.  M19+M20 have paid the infrastructure tax fully.

`collections` and `csv` followed the same minimalism:
* Counter is *typed* as `Dict[str, i64]` (no new heap shape).
* Deque is *typed* as `List[i64]` (no new heap shape); pop_front is
  an O(n) shift, documented in §9.16 as v0.3 work.
* csv reuses `List[List[str]]` for parsed-row results.

## Hardest three things

1. **The `--help` / clap collision.**  My first cut of the
   argparse_demo subprocess test ran `spy.exe demo.spyc --help` and
   asserted on the auto-generated help text.  It failed: clap (the
   `spy.exe` CLI driver, see `vm/src/main.rs`) reserves `--help` and
   `-h` for its own usage screen, even with `trailing_var_arg = true`
   and `allow_hyphen_values = true`.  The fix in the *test* is to add
   `--` as a clap-terminator: `spy.exe demo.spyc -- --help` passes
   `--help` through to `sys.argv`.  In real use this is mildly
   annoying (`my_tool` users expect `my_tool --help` to work), but
   fixing it would mean `disable_help_flag = true` on the global
   `spy.exe` CLI — a behaviour change that affects every user
   program, not just argparse consumers.  Documented in the test.
   Possibly worth a v0.3 follow-up: lift help to the *user-program*
   level via a CLI option like `spy run --` that turns off clap's
   own help.

2. **The `s[i]` vs `char(i32)` impedance mismatch in word_count.spy.**
   String indexing returns `u32`; `char()` is declared as `char(i32)
   -> char`.  The pattern `out + str(char(cp))` rejected `cp: u32`
   with `error[E2001]: expected u32, got char at :40:19`.  Looking
   at `examples/regex.spy` revealed the convention: store codepoints
   as `i32` and convert on the way in (`cp: i32 = i32(i64(s[i]))`).
   Five-minute fix in user code; worth calling out for future stdlib
   agents because Counter-style programs (word frequency, ngram
   analysis) all need this dance.

3. **Returning a freshly-allocated `Dict[str, str]` from `argparse.parse`
   while *also* iterating the input parser dict.**  My first cut held
   the dict lock through both the read-from-parser and the write-to-
   result phases, which deadlocked under `Mutex<Heap>`.  The fix is
   to copy the parser declarations into a Rust-side `HashMap<String,
   String>` first (one `with_dict_slot` call), drop the lock, then
   allocate the result and run the arg-walk.  The helpers
   `argparse_dict_set` / `argparse_dict_get` make this manageable —
   each takes/releases the lock explicitly per call.  Same shape as
   M19's `SysArgv` cache fix: read-state-then-allocate, not
   read-while-allocating.

## Incidentally-discovered bugs / oddities

* **No new bugs requiring code changes.**  The M22 trend (no new
  incidental bugs after the M20c milestone broke the streak) holds
  here.  M19+M20+M21 infrastructure absorbed three more modules
  without complaint.  The closest thing to a discovery is the clap
  `--help` interception above, which isn't really a bug — it's a
  CLI-policy choice that surfaced only because argparse is the first
  stdlib module whose semantic literally is `--help`.
* **String-vs-codepoint impedance** (call it BUG-029 candidate):
  every program that wants to walk a string char-by-char has to do
  `i32(i64(s[i]))` because `s[i]: u32` but `char()` takes `i32`.
  The simplest fix would be to add an explicit `char(u32)` overload
  in the prelude, or change the index-expr's return type to `i32`.
  Not a regression — predates M22 — but worth a separate task.

## Cross-platform notes

* The csv writer always emits `\n` (LF) row separators, not
  `\r\n`.  Matches Python's csv default lineterminator policy (`\r
  \n` is opt-in via `dialect`).  This is what every existing
  StrictPy example uses, and the read path handles both transparently.
* The argparse `_order_` field uses `\u{1F}` (ASCII US separator) as
  the join char.  This survives any reasonable string encoding —
  Rust's `String` is UTF-8, and U+001F is a single byte.  No
  cross-platform surprises here.
* `csv.read_file` uses `std::fs::read_to_string`, which requires the
  file's content to be UTF-8.  Non-UTF-8 CSV files raise IOError
  (Rust's underlying error message includes "stream did not contain
  valid UTF-8").  Fine for v0.2; v0.3 may want a `csv.read_bytes`
  variant.

## What's deferred to v0.3

* **Stdlib-class registration.**  A typed `ArgParser` / `Args` sealed
  class for argparse, and a `Counter[K, V]` generic class for
  collections, would both be Pythonic upgrades.  The M19
  `StdlibModule` shape is one extension away: add a
  `Vec<StdlibClass>` alongside its `Vec<StdlibItem>`, wire `class.X`
  lookups through `typecheck.rs`'s module-attr path.
* **Argparse subcommands** (`git commit`, `cargo build`).  Need a
  tree of sub-parsers; doable on top of the current dict-handle but
  ugly.  Better deferred until the typed `ArgParser` lands.
* **Real deque.**  Replace the O(n)-pop-front list-shift with a
  ring-buffer-backed type.  Probably warrants its own heap shape
  (similar to `ChannelRepr` / `DictRepr`), at which point the
  collections module gains a proper `Deque[T]` sealed class.
* **csv dialects.**  Configurable delimiter / quote-char /
  lineterminator (Python's `csv.Dialect`).  Mechanical once the
  default dialect is stable.
* **csv.DictReader / DictWriter.**  Header-driven row mapping.
