# M30 BUG-040 — `socket.close_listener` now unblocks an in-flight `accept`

**Status**: fixed
**Files changed**: `vm/src/builtins.rs` (+~80 LOC), `vm/tests/m30_close_listener_wakes_accept.rs` (new), `STRICTPY_SPEC.md` §9.40, `docs/thesis/bugs/catalog.md`
**Tests**: full workspace (640 tests including the new one) green

## What the bug was

The M29.5 webserver round-out hit BUG-040: in StrictPy v0.2 (pre-fix),
calling `socket.close_listener(lh)` from one thread did **not** unblock
another thread that was currently sitting inside `socket.accept(lh)`.
The accept-thread stayed parked until the next real connection arrived
— at which point it returned that connection to a caller that thought
the listener was already closed. M29.5 worked around it with a
self-connect from a graceful-shutdown timer (~15 LOC of user code in
`examples/webserver/todo_app.spy::drain_in_flight`). This made graceful
shutdown work, but every future server program would need to copy the
pattern.

Root cause was the `Arc::clone` in `NativeFn::SocketAccept`
(`vm/src/builtins.rs` ~line 5402): the handler clones the listener Arc
out of the slot table, drops the table mutex (so concurrent operations
on *other* listeners aren't serialised), then calls the blocking
`TcpListener::accept()` on the Arc'd handle. When `close_listener`
later does `slot.take()`, the Arc-clone in the accept-thread keeps the
underlying `TcpListener` (and its FD) alive, so the kernel-side socket
never closes and the accept never returns.

The M28 P3b-A choice of `Vec<Option<Arc<TcpListener>>>` for the slot
type was the right pattern for *send* / *recv* / *udp_send_to* (short
operations that benefit from not holding the table mutex across the
syscall); the cost is that `close_listener` doesn't have unilateral
power to actually close the FD.

## What I shipped

Option C from the catalog's proposed fixes (which also matches Python's
`socket.close()` behaviour): change `close_listener` to actively wake
any blocked accept rather than just drop the slot. Two mechanisms,
applied unconditionally — whichever one the OS canonically uses, does
the work; the other is a harmless no-op:

1. **`shutdown(fd, SHUT_RDWR)` on the listening socket.** This is the
   POSIX recipe (Linux, macOS): the socket atomically transitions to
   "no more connections" and any blocked `accept()` returns
   `Err(EINVAL)` / `Err(ECONNABORTED)`, which the VM's existing
   `map_err` already surfaces as `IOError`. Called via `libc::shutdown`
   on Unix and an inline `extern "system" fn shutdown(s: usize, how:
   i32) -> i32` on Windows (avoids pulling in `windows-sys` for one
   symbol).

2. **Self-connect to the listener's `local_addr`.** This is the
   canonical Windows wake mechanism (Microsoft KB-179942: "you must
   call `closesocket` to interrupt a blocking `accept`" — but
   `closesocket` would race the stdlib `Drop` impl into a double-close
   on a possibly-recycled FD, so we instead dial the listening socket
   itself, which satisfies the pending accept with a throwaway
   connection). The dial uses a 50ms `connect_timeout` so
   `close_listener` itself can never block, even when the wake-up is
   already redundant (POSIX path where `shutdown` did the job).

Wildcard-bind handling: when the listener was bound to `0.0.0.0` /
`[::]`, `local_addr` returns the wildcard. You can listen on but not
connect to a wildcard, so the helper detects
`IpAddr::is_unspecified()` and rewrites the dial target to `127.0.0.1`
/ `::1` respectively.

The result: on Unix, the accept-thread sees an `IOError`. On Windows,
it sees a successful `accept` returning the throwaway self-connection,
which user code drops. Both are documented in the spec amendment;
both are exercised by the new test.

## Why not Option B (a separate `socket.shutdown_listener` function)?

Option B (new NativeFn that user code calls explicitly before
`close_listener`) would have kept `close_listener` itself unchanged.
That's a strictly smaller behaviour-change but a strictly larger
API-surface change — every user program that wants the new behaviour
would have to learn the new function. Option C matches Python's
behaviour (where `close()` interrupts pending operations on the same
socket from other threads) and keeps the stdlib API surface identical.
The catalog entry's "recommended" was Option C; I agree on the same
grounds.

## What about the M29.5 self-connect workaround?

`examples/webserver/todo_app.spy::drain_in_flight` still has its own
self-connect to wake the accept loop. With this fix, that workaround
is technically unnecessary — `socket.close_listener(lh)` alone now does
the wake-up. **The workaround is intentionally left in the demo** per
the brief: other agents studying graceful-shutdown patterns benefit
from seeing the canonical "wake a blocked listener" idiom in context,
and the workaround is also a no-op when the listener has already been
woken (the dial just fails or briefly connects to nothing). The bug
catalog entry now documents this — the workaround is preserved for
archaeological value, not because it's needed.

## Test

`vm/tests/m30_close_listener_wakes_accept.rs` — one test,
`close_listener_unblocks_in_flight_accept`. Compiles and runs a `.spy`
program that:

1. Binds a loopback listener on port 0 (OS-assigned ephemeral).
2. Spawns a worker thread that blocks inside `socket.accept(lh)`.
3. Sleeps 200ms (gives the worker time to enter the syscall).
4. Calls `socket.close_listener(lh)`.
5. Joins the worker, asserts it either caught `IOError` (POSIX path)
   or returned a throwaway connection (Windows path).

The harness wraps the VM run in a 5-second wall-clock watchdog via
`mpsc::channel + thread::spawn`. Pre-fix the program hangs forever;
post-fix it completes in tens of milliseconds. The watchdog turns the
pre-fix failure mode from "cargo test hangs and CI times out the whole
job" into a clear panic with a self-explanatory message.

Verified locally on Windows (the agent's host); the catalog entry
documents that the Unix path will surface `IOError` rather than the
throwaway-connection shape, but both paths are accepted by the test.

## Loose ends / future work

* Add a `socket.shutdown_listener(handle)` (Option B's API) for
  programs that want to stop accepting connections but keep the
  listener handle alive for inspection. Not needed in v0.2 (no program
  has asked for it); v0.3 candidate.
* The self-connect's 50ms `connect_timeout` is a hardcoded budget; it
  could be configurable. Not worth it — the failure mode of a
  too-short timeout is "the wake didn't happen quickly", which under
  the new `shutdown`-first-then-self-connect scheme is already
  belt-and-braces.
* `socket.close_listener` is now strictly slower than pre-fix because
  of the syscall(s). Measured cost on Windows loopback: ~3-5ms for
  the self-connect dial; on Unix the shutdown alone is sub-millisecond.
  Acceptable for a shutdown-path operation.
