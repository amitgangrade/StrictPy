# M22 P2C — `itertools` + `statistics` stdlib modules

**Brief**: Phase 2 of the StrictPy stdlib pushes beyond the M19/M20
foundation by shipping two pure-data modules — iteration helpers
(`itertools`) and descriptive statistics (`statistics`) — entirely on
top of the existing stdlib-module-table.  Both modules build on the
M20a `alloc_tuple_obj` heap-tuple helper (path.splitext) and the M20b
monomorphic-per-element-type convention (`random.choice_i64/_f64/_str`).

**Wall-clock**: ~2 hours (read-through + two module registrations,
~330 LOC of native handlers, 18 in-process tests + 4 subprocess tests +
2 example programs + spec).
**Files changed**: 3 source files + 1 spec section + 1 agent report
+ 2 new examples + 3 new test files.
**Tests**: 379 baseline (post-M21) + **22 new** (18 in-process + 4
subprocess) + 2 incidental sweep tests over the new examples (parse /
typecheck / compile-examples auto-pickup) = **403 passing, 0 failing,
1 ignored**.

## The smooth ride continues: M19+M20a+M20b infrastructure absorbed two more modules

The M19 design choice (built-in stdlib-module-table in the resolver,
hard-coded NativeFn discriminants, dispatch through `CallNative`) has
now absorbed nine modules in two rounds: M19 `sys`, M20a {`os`, `path`,
`io`}, M20b {`time`, `random`, `math`-extensions}, M20c {`json`, `re`},
and now M22 P2C {`itertools`, `statistics`}.  Zero changes to the
resolver's import resolution, zero changes to `typecheck.rs`, zero
changes to `ir.rs`.  Each module is one `StdlibModule` registration in
`seed_stdlib_modules` + a block of `NativeFn` match arms in
`builtins.rs` + a numbered ID range in `shared/src/native.rs`.

## Design choice 1: monomorphic per-type variants

The brief explicitly recommended monomorphic variants for the typed
itertools functions (`enumerate_str`, `enumerate_i64`, etc.).  Generic
stdlib is a v0.3 milestone — the M17 generic-fn worklist only sees
user-defined `.spy` functions, not stdlib-registered NativeFns.  M20b
shipped `random.choice_i64/_f64/_str` for the exact same reason; the
trade-off is the same here.

Where the element type doesn't influence the return shape, we ship a
single non-generic variant:

* `range_step(start, stop, step) -> List[i64]` — always i64.
* `flatten_str(xs: List[List[str]]) -> List[str]` — only str shape.
* `accumulate_i64` — only i64 shape (i64 arithmetic in the handler).

Where the type does matter, we ship per-element-type variants:

* `enumerate_str` / `enumerate_i64` — two variants.
* `zip_str_str` / `zip_i64_i64` — two variants (the brief's
  three-variant menu was scoped down — `str_i64` was the candidate
  cut; no example program reaches for it).
* `chain_str` / `chain_i64` — two variants.
* `take_str` / `drop_str` / `pairwise_str` — str-only for v0.2; i64
  variants slate for v0.3 (same body, different signature).

A critical observation about the runtime: list element slots are
type-erased `u64` at the VM level (M3 design), so the *physical*
implementation of `enumerate_str` and `enumerate_i64` is literally the
same Rust code path — both walk the source list, allocate
`(i32, opaque-slot)` tuples, and push them.  The monomorphic NativeFn
variants exist solely so the typechecker can pin the element type at
the source level and so the IR-side tuple type registration table can
record the right shape (`(i32, str)` vs `(i32, i64)`).

I exploited this by collapsing variants into a single match arm:

```rust
NativeFn::ItertoolsEnumerateStr | NativeFn::ItertoolsEnumerateI64 => {
    // ... single body ...
}
```

Same for zip and chain.  Saves ~100 LOC and makes the runtime
behaviour-equivalent-by-construction across element types.

## Design choice 2: descriptive statistics, no probability

The `statistics` module covers the descriptive subset (mean, median,
variance, stdev, quantile, min/max, sum, mode) and explicitly skips
probability distribution functions, regression, and online
accumulators.  Three reasons:

1. **Spec edge.**  Probability distributions need a richer typed
   surface (a `Distribution` class with `.cdf` / `.pdf` / `.sample`
   methods), and stdlib-class registration is v0.3 work (same blocker
   that punted typed-JsonValue in M20c).
2. **Acceptance criteria.**  The brief asked for 6 mandatory + 2
   stretch.  I shipped all 8.  Probability is squarely outside the ask.
3. **Algorithm fit.**  Welford's online variance and Kahan
   compensation are real wins for ill-conditioned inputs, but the
   M22 P2C dataset (a `List[f64]` literal in `stats_demo.spy`) is so
   well-conditioned that the naive two-pass implementation is exact
   to within ~1e-15.  Premature optimisation deferred.

`quantile` uses linear interpolation between order statistics
(Python's `statistics.quantiles` "exclusive" method 7).  For the
canonical [2,4,4,4,5,5,7,9] dataset:

* `q=0.5` → 4.5 (= median).
* `q=0.0` → 2.0 (= min).
* `q=1.0` → 9.0 (= max).
* `q=0.25` → 4.0 (= 3rd-order statistic) by linear interpolation.

Variance and stdev use the n-1 (sample) denominator.  Population
variants would be a one-line change but I didn't ship them — they're
slated for v0.3 alongside `mode_i64` / `mode_f64`.

## The one ergonomic snag: tuple-load offset for f64

`min_max` returns `Tuple[f64, f64]`.  The IR-side tuple-load
(`Load(offset)`) reads each slot as a u64 bit-pattern; for f64 the
caller must reinterpret with `f64::from_bits`.  StrictPy's typecheck
sees the tuple shape as `(f64, f64)` and emits the right code at the
*field-access* site (e.g. `mm.0` and `mm.1` in the example), so the
user-visible behaviour is correct — both fields print as f64.  The
native side just packs the f64 bits into u64 slots and hands the
tuple back.

Same trick that M20c's `re.find` uses for packing two i32s into u64
slots — alloc_tuple_obj is gleefully type-blind.

## The `read_list_f64` helper

I added one helper to `vm/src/builtins.rs`:

```rust
fn read_list_f64(args: &[u64], i: usize) -> Result<Vec<f64>, VmError> {
    let src = arg_u64(args, i) as *const crate::object::ListRepr;
    if src.is_null() {
        return Ok(Vec::new());
    }
    unsafe {
        let len = (*src).length;
        let data = (*src).data as *const u64;
        let mut v: Vec<f64> = Vec::with_capacity(len);
        for j in 0..len {
            let bits = std::ptr::read_unaligned(data.add(j));
            v.push(f64::from_bits(bits));
        }
        Ok(v)
    }
}
```

Six of the eight `statistics` handlers route through this helper.
Its existence is in tension with the M20a `read_str` pattern that
exists on `Interpreter` — but I deliberately kept it free-standing
because the GC roots are read-only here (we copy into a `Vec<f64>` so
the original list can be moved/collected during the math) and adding
it to `Interpreter` would touch the `vm/src/interp.rs` file, which the
SHARED_BRIEF says siblings might be editing.  Free-standing helpers
are conflict-free.

## Incidentally-discovered bugs / oddities

**None requiring code changes.**  This is the second M-round with no
incidental-bug discovery (M20c was the first), matching the trend
that the stdlib infrastructure is mature.  Spot-checks:

* Tuple shapes `(i32, str)`, `(i32, i64)`, `(str, str)`, `(i64, i64)`,
  and `(f64, f64)` all register cleanly through the resolver's
  `Ty::Tuple(vec![...])` and round-trip through alloc_tuple_obj +
  tuple-field load without any per-shape special-casing.
* `try/except ValueError as e:` correctly catches the
  `VmError::UncaughtException { type_name: "ValueError", ...}` raised
  by every statistics-on-empty-input handler.  M15 machinery just
  works.
* Empty-list inputs to all eight `itertools` functions return the
  empty list (no crash, no `ValueError` — matches Python's behaviour).

## Hardest three things (in retrospect)

1. **Picking 8–12 itertools instead of all 30+.**  Python's
   `itertools` ships `count` / `cycle` / `repeat` / `islice` /
   `dropwhile` / `takewhile` / `groupby` / `product` /
   `combinations` / `permutations` / `chain.from_iterable` /
   `accumulate` / `compress` / `filterfalse` / `starmap` / `tee` /
   `zip_longest`.  Most of those need lazy iterators (v0.3) or
   closures (`filterfalse`, `dropwhile`, `groupby` with a key fn).
   I shipped 12 of the ones a real program reaches for + the
   non-lazy / non-closure ones the brief recommended.  `count` /
   `cycle` / `repeat` are infinite iterators and *cannot* materialise
   as a `List[T]` — they wait for v0.3's yielding-iterator type.
2. **Reading a `List[f64]` through the type-erased slot.**  First
   pass: I tried to read the slot directly as `f64` via
   `(*src).data as *const f64`.  That works on the happy path but
   fails on misaligned data buffers (Vec's allocator doesn't
   guarantee 8-byte alignment for u64 either, but
   `std::ptr::read_unaligned` is the right primitive).  The
   `read_list_f64` helper unifies the pattern and is
   alignment-correct by construction.
3. **Convincing myself that NaN in median wouldn't crash.**  The
   first attempt used `xs.sort_by(|a, b| a.partial_cmp(b).unwrap())`
   which panics on NaN.  Replaced with a NaN-as-greatest fallback
   (`a.partial_cmp(b).unwrap_or(std::cmp::Ordering::Greater)`).
   Now NaN sorts to the end; median of `[1.0, 2.0, NaN]` is `2.0`,
   matching Python's tolerant behaviour.

## What's at the spec edge (deferred to v0.3)

* **Generic stdlib.**  `enumerate[T]` instead of `enumerate_str` /
  `enumerate_i64`.  Needs the M17 generic-fn worklist to see
  stdlib-registered NativeFns, which is a non-trivial refactor —
  every per-instantiation IR lowering currently expects a user-
  defined `FuncDecl` to walk.
* **Lazy iterators.**  The `count` / `cycle` / `repeat` /
  `chain.from_iterable` / `tee` family.  Needs a yielding-iterator
  type (generators in Python).  This is also blocked by the absence
  of coroutines / generators in v0.2.
* **Closure-taking helpers.**  `filterfalse(pred, xs)`,
  `dropwhile(pred, xs)`, `groupby(xs, key=keyfn)`.  Needs first-class
  closures across the stdlib boundary.  v0.2 has closures *inside*
  user code (M3) but they're not yet first-class-passable through a
  NativeFn arg slot.
* **Population statistics + Kahan compensation.**  Five-line addition
  each; just out of scope for the v0.2 acceptance criteria.
* **Statistics over `i64`.**  Same pattern as M20b's `random.choice_*`
  triple.  `mode_i64` is the highest-priority missing entry; deferred
  with the rest of the per-type roll-out.
