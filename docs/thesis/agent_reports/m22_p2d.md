# M22 P2D — `struct` + `urllib_parse` stdlib modules

**Brief**: Ship binary pack/unpack (`struct`) and URL helpers
(`urllib_parse`) on top of the M19 stdlib-module-table infrastructure.
Native ID range **330-349** (20 slots), disjoint from sibling Phase 2
agents.  This is the first Phase 2 round that touches binary data —
the previous nine stdlib modules (sys/os/path/io/time/random/math/json/re)
were all text- or syscall-shaped.

**Wall-clock**: ~1.5 hours (read-through SHARED_BRIEF + M19/M20a/M20c
reports + struct module + urllib_parse module + 17 in-process tests +
4 subprocess tests + 2 example programs + spec §9.15-§9.16).
**Files changed**: 4 source files + 1 spec section + 1 agent report +
2 new examples + 3 new test files.
**Tests**: 379 baseline (M21) + **21 new** (17 in-process VM + 4
subprocess) = **400 passing, 0 failing** (verified with
`cargo test --workspace --release`).

## Native ID layout (12 + 6, 2 reserved)

| Range | Module | Count |
|---|---|---|
| 330–335 | `struct` pack (u32/u64/f64 × BE/LE) | 6 |
| 336–341 | `struct` unpack | 6 |
| 342–345 | `urllib_parse` quote/unquote × plus | 4 |
| 346–347 | `urllib_parse` urlencode / parse_query | 2 |
| 348–349 | reserved (v0.3: parse_url, join_url, OR u16 pack/unpack) | — |

Two IDs intentionally left fallow — v0.3 has options to spend them on
either the URL pair (`parse_url` / `join_url`) or the stretch
`pack_u16` pair, and the brief explicitly defers both.  Better to
leave the slots open than to renumber later.

## Design choice 1: `str` as binary (option (a)) — does work

The brief flagged this as the central design risk: StrictPy's `str` is
nominally Unicode-text-shaped, but `struct.pack_u32_be(0xAABBCCDD)`
naturally wants to return 4 raw bytes including high-value bytes that
don't form valid UTF-8 on their own.  The brief offered two paths:

* **(a)** Ship as `str`, document the result is "not valid UTF-8 in
  the high byte range."
* **(b)** Punt to signed-int variants only (every result is ASCII).

I went with **(a)** under a slightly different framing.  Rather than
producing invalid UTF-8, I encode each byte as one Unicode codepoint
in `U+0000..U+00FF` — i.e. the C0 + Latin-1 ranges.  Concretely:

* Byte `0x41` ('A') becomes char `U+0041` ('A') — one UTF-8 byte.
* Byte `0xFF` becomes char `U+00FF` ('ÿ') — two UTF-8 bytes.

The resulting `str` is valid UTF-8 and round-trips through every VM
primitive cleanly (concatenation with `+`, `len()` for byte count,
indexing if a user ever wants it).  The trade-off: the on-disk UTF-8
representation is wider than the logical byte buffer (a 4-byte u32
pack of `0xFFFFFFFF` takes 8 UTF-8 bytes), so the result is NOT a
wire-format byte buffer.

This was the right call for v0.2: it preserves every "user-level"
property (`len(buf) == 4` for a u32 pack, concatenation makes sense,
unpack-from-offset works on char positions) without requiring a new
`bytes` runtime type.  The spec §9.15 documents the gap; v0.3 will
add real `bytes` and the pack functions will return that instead
(function names unchanged).

The implementation uses `char::from(b: u8)` to build each codepoint
and `s.chars()` to walk back to bytes.  `read_str` (the VM's UTF-8
decoder for heap strings) was already lossy-tolerant from M19 — no
infrastructure changes needed.

## Design choice 2: tuple slots from native code

`urllib_parse.urlencode` takes `List[Tuple[str, str]]` and needs to
read the two `str` slots of each tuple from inside a native handler.
M20a established the helper `Interpreter::alloc_tuple_obj` (write
side, used by `path.splitext`), but the read side is new territory —
the VM normally reads tuple slots via `Load(offset)` IR ops, which
aren't reachable from inside `dispatch`.

Direct pointer arithmetic works: each tuple is `HDR + N*8` bytes, and
the slots live at `tuple_ptr + HDR + slot_index*8`.  I added a
`OBJECT_HEADER_SIZE = std::mem::size_of::<ObjectHeader>()` constant
in `builtins.rs` (the canonical `HDR` const in `interp.rs` is
private; rather than break encapsulation I derived it locally so the
two consts can't drift — `size_of` is evaluated at compile time).

**The bug that wasn't.**  My first cut hard-coded `OBJECT_HEADER_SIZE
= 24` from a half-remembered glance at the codebase.  Tests passed
for everything except `urlencode_round_trip_with_parse_query`, which
printed garbage values like "v=" instead of "k=v".  The fix was
trivial — `ObjectHeader` is 16 bytes, not 24 — but worth noting:
hard-coded sizes are exactly the trap `size_of` is for, and I should
have used it from the start.  Replaced the constant with `size_of<
ObjectHeader>()`.

## Design choice 3: URL encoding — hand-rolled, not `url` crate

The brief flagged that pulling in the `url` crate would be heavy.
Hand-rolling percent-encoding is genuinely 25 lines of code (the
`url_quote` + `url_unquote` helpers in `builtins.rs`).  The RFC 3986
unreserved set is `A-Z a-z 0-9 - _ . ~`; everything else gets `%HH`
encoded.  `quote_plus` / `unquote_plus` add the `' '` ↔ `+`
substitution as a flag.

The interesting bits:

* `url_quote` operates on the UTF-8 byte representation of the input.
  So `quote("☃")` produces `%E2%98%83` (the 3 UTF-8 bytes of
  U+2603).  This matches Python's behaviour.
* `url_unquote` collects decoded bytes into `Vec<u8>`, then re-parses
  as UTF-8.  Malformed sequences fall back to `String::from_utf8_lossy`
  (the same `read_str` policy used elsewhere).
* Malformed `%XY` (where `X` or `Y` isn't hex) raises `ValueError`.
  Truncated `%X` at end-of-string also raises.

For `urlencode` / `parse_query` I use `quote_plus` / `unquote_plus`
on both keys and values — the form-encoding convention dominates
real-world query string usage (Python's `urlencode` is the same).

## What v0.2 does NOT ship (and why)

* **`pack_u16` / `unpack_u16`** — stretch goal in the brief, dropped
  to keep the ID range under control.  Reserve IDs 348/349 are open.
* **`pack_i32` / signed-int unpacks** — wrap on the caller side
  (`pack_u32_be(value & 0xFFFFFFFF)`).  Adding signed variants is a
  v0.3 ergonomics tweak.
* **Variable-width format strings** (`">If"`).  Fits poorly into the
  fixed-arity native discipline; v0.3 may add a parser.
* **`parse_url(url) -> (scheme, host, port, path, query)`** — real
  URL parsing is genuinely hairy (port, userinfo, IPv6 literals,
  default-port resolution).  Deferred to v0.3.
* **`join_url(base, ref)`** — depends on `parse_url`.  Deferred.

## Hardest three things (in retrospect)

1. **The `OBJECT_HEADER_SIZE` mistake.**  Five minutes of "why does my
   urlencode round-trip print garbage" before I read `object.rs` and
   saw `const _: [(); 16] = [(); std::mem::size_of::<ObjectHeader>()];`.
   Lesson: never hard-code a sizeof; let the compiler derive it.

2. **Deciding the byte-as-codepoint encoding.**  Option (a) needed
   thought — at first I worried that high-byte chars would corrupt
   subsequent string operations, but `alloc_string` uses Rust's
   `&str` which is UTF-8 by construction, and `char::from(0xFF)` is
   a valid `char` (Latin-1 supplement).  The only place where the
   "looks like text" abstraction leaks is if a user `print`s a
   packed buffer — they'll see a string of accented Latin-1
   characters.  That's fine, and arguably better than crashing.

3. **Reading tuple slots from native code.**  M20a's
   `alloc_tuple_obj` is the write side; the read side wasn't
   documented anywhere.  I worked it out by reading the IR lowering
   for `Load(offset)` and the GC scan code (uniform 8-byte slots
   starting at `HDR`).  Once that clicked, the urlencode handler is
   six lines: walk the list, read each tuple's two slots, format
   `quote_plus(k) + "=" + quote_plus(v)`, join with `&`.

## Incidentally-discovered bugs / oddities

* **None requiring code changes.**  The M19+M20+M21 infrastructure
  absorbed two more modules without complaint, *including* a new
  list-of-tuple-of-string input shape that no prior native has
  needed.  This is the second Phase 2 sub-milestone with no
  incidental-bug discovery (M20c was the first; the M19/M20a/M20b
  one-bug-per-round trend broke at M20c).  Two consecutive clean
  rounds suggests the stdlib infrastructure has stabilised — Phase
  3 work will move to user-defined modules + submodules, which
  exercise *different* code paths.

* **The "placeholder lowering" pattern count remains at 3** (M19's
  joined `io.File` resolution, M20a's `??` null-coalesce, M20b's
  bare-name `sqrt` prelude shadowing).  No new instances in P2D.

* `pack`'s "str of high-byte chars" behaviour is mildly surprising
  when debugged via `println(buf)`: you see Latin-1 accents, not raw
  bytes.  The example program demonstrates `len(buf)` explicitly so
  users learn the right mental model (length = byte count, content
  isn't intended to be human-readable).

## Cross-platform notes

* The two modules are pure functions over `str` — no syscalls, no
  filesystem, no clocks.  Same behaviour on Windows, Linux, macOS.
* Endianness: `u32`/`u64` pack values use Rust's
  `u32::to_be_bytes` / `to_le_bytes` — the runtime endianness of the
  host CPU is irrelevant.  This was the entire point of having
  explicit BE/LE variants: cross-architecture protocol code stays
  deterministic.
* IEEE 754 `f64` pack uses `f64::to_bits` then the same byte-swap
  logic.  NaN bit patterns survive round-trip (the host CPU's
  NaN-canonicalisation behaviour is bypassed).

## What's next

Two pieces of v0.3 work that the M22 P2D arc highlights as natural:

1. **A real `bytes` runtime type.**  Pack/unpack would return
   `bytes` instead of `str`, and the "byte-as-codepoint"
   workaround disappears.  This also unblocks `pack_i8/i16/i32` and
   any future protocol-buffer-style native that needs raw bytes.
2. **`urllib.parse` submodule under the M19 stdlib-module-table.**
   The `urllib_parse` name uses `_` because submodules aren't
   resolvable yet.  Once user-defined modules land (v0.3), promoting
   `urllib_parse` → `urllib.parse` is a one-line resolver change
   and a back-compat alias.

P2D is the cleanest stdlib round to date — two modules, ~580 LOC
across the compiler + VM, 21 new tests, zero infrastructure changes,
zero incidental bugs.  The M19 design tax keeps paying out.
