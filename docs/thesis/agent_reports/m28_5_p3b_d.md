# M28.5 P3b-D — `ssl` server-side TLS (StrictPy can now host HTTPS)

**Brief**: close the v0.3-deferred gap that M28 P3b-B explicitly left
on the table.  After P3b-B, StrictPy could `ssl.connect(host, port)`
as a client; it could not present a certificate to an inbound peer
because rustls's `ServerConnection` + `ServerConfig` surface had no
StrictPy-side binding.  P3b-D wires three new native functions —
`ssl.load_server_config`, `ssl.accept_tls`, `ssl.free_server_config`
— and teaches the shared `send` / `recv` / `close` / `peer_addr` /
`set_timeout_secs` / `peer_cert_subject` / `recv_exact` handlers to
dispatch transparently on either side.

**Wall-clock**: ~25 min of agent compute.  The crate graph was
already warm from P3b-B (rustls 0.23 + ring + webpki-roots), so the
only fresh build cost was `rustls-pemfile 2` + a vm-crate
re-link.  The slowest single step was reading the existing P3b-B
code carefully enough to be confident that "Option A" (parallel slot
table) was the lowest-risk integration shape.

## API surface (3 functions, IDs 610-612)

| ID  | Name                  | Signature |
|-----|-----------------------|-----------|
| 610 | `load_server_config`  | `(cert_pem_path: str, key_pem_path: str) -> i64` |
| 611 | `accept_tls`          | `(tcp_listener: i64, server_config: i64) -> Tuple[i64, str]` |
| 612 | `free_server_config`  | `(config: i64) -> None` |

The P3b-B brief reserved 610-619 for "server-side TLS, mutual auth,
SNI override, custom-CA bundles, session resumption" so this is
exactly the first three of that reservation; IDs 613-619 remain for
v0.3.

## Slot-table design — Option A wins

The brief laid out three candidate shapes for the server-side
stream table.  I went with Option A: keep `tls_streams: HashMap<i64,
StreamOwned<ClientConnection, TcpStream>>` byte-identical to what
P3b-B shipped, and add a parallel `tls_server_streams: HashMap<i64,
StreamOwned<ServerConnection, TcpStream>>` next to it on `SharedVm`.
The reason it won over Option B (single enum-keyed table) and
Option C (`rustls::Connection` enum + `StreamOwned<Connection, ...>`):

* **Zero risk to P3b-B's client tests.**  Every line of the P3b-B
  client handlers is touchable by my changes but only in additive
  ways — the existing match arms grew an `if handle >= 1_000_000`
  preamble that picks the server table, and fall through to the
  exact original code path when the handle is on the client side.
  If the cherry-pick to main re-orders or drops one of my preamble
  blocks, the worst case is a server-side request fails with a
  ValueError; the client side keeps working.
* **No tag bytes in the handle**.  The brief suggested
  `next_tls_server_id: AtomicI64::new(1_000_000)` so server handles
  draw from a disjoint id range.  I took that — server handles start
  at `1_000_000`, client handles start at `1`, and the shared
  handlers dispatch on `handle >= 1_000_000` alone.  No enum tag,
  no double lookup, and a freed handle on either side gives a
  clean ValueError out of its own table's lookup.
* **Option C was tempting** — `rustls::Connection` does implement
  `DerefMut` over either inner conn, so a single `StreamOwned<Connection,
  TcpStream>` would have unified the table type.  But it would have
  required editing every existing P3b-B handler to swap
  `ClientConnection`-typed locals for `Connection`-typed ones, and
  the `peer_certificates()` accessor would have needed a different
  call path on each side anyway.  More edits + less M28 P3b-B
  preservation = worse on every axis.

## Handle-range dispatch (the load-bearing trick)

Every shared handler in `vm/src/builtins.rs` got the same shape:

```rust
NativeFn::SslSend => {
    // ... read args ...
    if handle >= 1_000_000 {
        // server-side table lookup + identical I/O
        return ...;
    }
    // original P3b-B client-side body, byte-for-byte
}
```

The `1_000_000` constant is duplicated across six match arms.  I
could have hoisted it to a `const SSL_SERVER_HANDLE_BASE: i64 =
1_000_000;` somewhere, but the duplication is intentional: it gives
the orchestrator's cherry-pick six independent anchors instead of
one shared symbol that becomes a single point of failure.  Each
preamble carries a `// M28.5 P3b-D` marker plus the distinctive
`p3b_d_` prefix on every local so a patience or myers diff has zero
ambiguity about which match arm a given preamble belongs to.

`p3b_d_lsc_*` (load_server_config), `p3b_d_acc_*` (accept_tls),
`p3b_d_fsc_*` (free_server_config), `p3b_d_send_*` / `p3b_d_recv_*`
/ `p3b_d_rex_*` / `p3b_d_paddr_*` / `p3b_d_tmo_*` / `p3b_d_pcs_*`
identify the per-handler preambles.

## Why server handles start at 1_000_000

The brief suggested any high value; I picked `1_000_000` because:

* It's far enough above the next client id (P3b-B starts at 1) that
  a single process running for a *long* time still can't collide.
  Even at 10k client connects/sec (way more than any v0.2 use
  case is built for), it'd take 27+ hours to reach `1_000_000`.
* It's small enough to fit in a Python int literal in user code
  if anyone ever wants to test the boundary by hand.
* It's a clean threshold for the dispatch test (`handle >= 1_000_000`
  is one comparison; no bitmask, no top-bit-set shenanigans).

If a future v0.3 use case ever pushes client connects past a million
per process, the right fix is to bump the server base to
`1_000_000_000` (still safe for i64) and re-grep for the constant.
For v0.2's expected workloads this is comfortable.

## PEM parsing via `rustls-pemfile`

`load_server_config` reads both files with `std::fs::read`, runs
the bytes through `rustls_pemfile::certs` (returns an iterator of
`Result<CertificateDer<'static>, _>`) and `rustls_pemfile::private_key`
(returns `Result<Option<PrivateKeyDer<'static>>, _>` — the option
distinguishes "PEM was valid but had no key in it" from "PEM was
malformed").  Both intermediate types are the ones rustls's own
`ServerConfig::with_single_cert` accepts, so no manual conversion is
needed.

The cert iterator is collected into `Vec<CertificateDer>` (handles
intermediate chains in PEM input order).  An empty vec — no certs
found — raises ValueError with a path-in-message hint that's
copy-pasteable into a follow-up "let me look at that PEM" debug
session.

`rustls-pemfile` was the only new crate dep needed.  `rcgen` is
already a compiler dev-dep from P3b-B so the integration test
needed no new dev-deps either.

## Eager handshake on the server side

`accept_tls` calls `stream.flush()` right after wrapping the new
`ServerConnection` around the accepted TCP socket, exactly mirroring
the client side's `connect`-time `flush()`.  This drives the
handshake to completion before returning the handle to user code,
so a bad client hello, protocol mismatch, or peer-hung-up
surfaces as `IOError` out of `accept_tls` rather than the first
`ssl.recv` call after a confusing "accept succeeded" log line.

The brief showed this pattern in pseudocode; the actual code matches
the brief almost verbatim except for the error mapping (every
`std::io::Error` and every `rustls::Error` is mapped to a StrictPy
`IOError` with a function-name + reason message).

## What the test verifies

`compiler/tests/https_server_demo_runs.rs` runs both halves of the
exchange inside a single `spy.exe` process: the StrictPy demo spawns
a client thread, the main thread runs `accept_tls`, and the two
exchange a fixed-length `GET / HTTP/1.0\r\n\r\n` request + 34-byte
canned response.  The Rust harness only:

1. Generates a self-signed cert for `CN=localhost` via
   `rcgen::generate_simple_self_signed`.
2. Writes the cert as PEM (`cert.cert.pem()`) and the key as PEM
   (`cert.key_pair.serialize_pem()`) to a tempdir under
   `CARGO_TARGET_TMPDIR`.
3. Invokes `spy.exe https_server_demo.spyc <cert_path> <key_path>`.
4. Asserts the stdout contains every expected waypoint:
   `server_cfg: loaded`, `bound: true`, `accepted: true`,
   `server.peer_addr: nonempty`, `server.recv_exact: ok`,
   `server.send: ok`, `server.close: ok`, `client.status: ok`,
   `round_trip: ok`, `done`.

Loopback only — no DNS, no public TLS endpoint, no firewall-
traversable traffic.

The shared-cell pattern (`port_cell: List[i32]`, `ready_cell:
List[i32]`, `reply_cell: List[str]`, `status_cell: List[str]`)
matches what `socket_demo.spy` already established for the M28 P3b-A
worker-thread integration test.  Same handshake: main binds first,
flips `ready_cell[0] = 1i32`, the worker spin-waits on that.

## Methodology — commit-before-report (Lesson 1)

First commit landed at the moment the workspace build went green —
roughly 40% of compute budget, well before the 60% deadline.  The
demo + integration test + spec amendment landed in a second commit
once `cargo test --workspace --release --test https_server_demo_runs`
passed.  The third (this) commit covers the report file only, so
even if my time budget runs out mid-write the orchestrator already
has every artifact except the report itself.

## Methodology — distinctive prefix (Lesson 2)

Every local in the new code and the new preambles on existing
handlers uses the prefix `p3b_d_` plus a per-function suffix
(`p3b_d_lsc_*`, `p3b_d_acc_*`, `p3b_d_fsc_*`, `p3b_d_send_*`,
`p3b_d_recv_*`, `p3b_d_rex_*`, `p3b_d_paddr_*`, `p3b_d_tmo_*`,
`p3b_d_pcs_*`).  None of these collide with any verbatim line in
the existing 30+ stdlib modules or in P3b-B's client surface — the
patience / myers cherry-pick alignment has unique anchors for
every block.

Closing-brace shapes follow the established `}` on its own line
convention at every match-arm boundary, including the last new arm
(`NativeFn::SslFreeServerConfig`).  No double-`}` or single-`}` at
EOF that a naive merge could swallow.

## Cross-platform notes

`rustls-pemfile` is pure Rust.  `rustls::ServerConnection` /
`ServerConfig` are pure Rust.  The ring crypto provider is pure Rust.
No `aws-lc-sys`, no system `libssl`.  Build + runtime behaviour are
identical across Windows / Linux / macOS — same property P3b-B
established for the client side.

## Test totals

`compiler/tests/https_server_demo_runs.rs` adds 2 tests:
`https_server_demo_compiles` and `https_server_demo_runs_via_spy_exe`.
Both pass on first invocation, in isolation, in the full workspace
test run, and with the `--release` profile that the rest of the
suite uses.

The pre-existing flaky test `algorithms_lib_runs::algorithms_lib_all_tests_pass`
intermittently fails under high test-parallelism because it shares a
fixed `algorithms_lib.spyc` filename in `CARGO_TARGET_TMPDIR` with no
serialization mutex — a 0-byte read race between the write step of
one test instance and the read step of another.  It passes
deterministically in isolation (verified after my changes) and is
unrelated to the ssl surface.  Triage of that race is a v0.3 hygiene
candidate, not a P3b-D regression.

## What's NOT shipped (intentional v0.3 scope)

* **Mutual auth** (client certificates).  `ServerConfig::builder...
  with_no_client_auth()` is hard-coded; mutual auth needs both a
  config knob (`with_client_cert_verifier(...)`) and a per-connection
  accessor for the verified client cert chain.  v0.3.
* **SNI override / multi-cert per-host server**.  The current config
  serves one cert chain for every accepted connection.  Switching
  by SNI needs a `ResolvesServerCert` impl with a host -> cert map.
* **ALPN.**  No `protocols` knob; HTTP/2 negotiation is not supported.
* **Session resumption / 0-RTT.**  Default cipher suites only.
* **OCSP stapling.**  Not exposed.
* **A streaming PEM loader.**  `load_server_config` reads the whole
  cert + key file into memory; this is fine for any realistic
  cert chain (a few KB) but a v0.3 streaming variant would be
  trivial to add if anyone needs to load multi-MB chains.

## Incidental findings

* `rcgen 0.13` exposes `Certificate::pem()` directly on the issued
  cert (no separate `serialize_pem`) and `KeyPair::serialize_pem()`
  on the key.  Both return owned `String`s and can be written
  straight to disk with `std::fs::write`.  No StrictPy-side bug;
  documented here for future agents who copy the test skeleton.
* `rustls-pemfile 2.x` is the renamed successor of the 1.x crate —
  the iterator-returning `certs` and `Option`-returning `private_key`
  shapes are unchanged from the rcgen test code already in the repo,
  so the integration was a straight drop-in.
* `rustls::StreamOwned<ServerConnection, TcpStream>` exposes the
  same `.sock` (TcpStream) and `.conn` (ServerConnection) fields as
  the client-side `StreamOwned<ClientConnection, TcpStream>`, so the
  `peer_addr` / `set_timeout_secs` / `peer_certificates` paths in
  the shared handlers needed only the handle-range dispatch, no
  field-access rewrites.
* No StrictPy-language bugs surfaced.  Resolver absorbed the three
  new `StdlibItem` entries on the existing `ssl` module without
  complaint; the existing `Tuple[i64, str]` shape from `socket.accept`
  was reusable for `ssl.accept_tls` (same accept-returns-pair
  contract).
