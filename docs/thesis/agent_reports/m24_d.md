# M24-D — `fs_migrator` filesystem-migration tool

**Brief**: Stress the M23 Phase 3a stdlib surface by composing
**pathlib + os + datetime + subprocess + io + sys** in a single
program.  Walk a 3-level directory tree, classify files by age,
emit a pretty tree-style report.  10 numbered probes exercise the
combination.

**Wall-clock**: ~2 hours (read-through + design + ~330 LOC of
`.spy` + the integration test + bisecting one cross-platform
fragility + writeup).
**Files added**:

* `examples/fs_migrator.spy` — the migration tool (340 LOC,
  10 numbered probes).
* `compiler/tests/fs_migrator_runs.rs` — 2 integration tests
  (compile + run-via-spy.exe).
* `docs/thesis/agent_reports/m24_d.md` — this report.

**No source-tree changes.**  Every probe ran on the M23 surface
as-shipped; the workarounds I reached for are documented below
as suggestions for Phase 3b rather than blockers.

## The program in one paragraph

`fs_migrator.spy` creates a known 3-level test tree
(`_m24_fs_migrator_tmp/{a.txt,notes.md,sub1/{inner.txt,
archive.tar.gz,sub2/deep.log}}`), walks it via a recursive
`os.listdir + os.is_dir` pair (v0.2 has no `os.walk`), pulls each
file's modification time by shelling out to `dir /T:W` (Windows)
or `stat -c %Y` (Unix) via `subprocess.run`, then computes age in
days against `datetime.now()` and classifies into
{`old (>30 days)`, `medium`, `recent (<7 days)`}.  The report is
emitted with `pathlib.name` / `pathlib.stem` / `pathlib.suffix`
decomposition per file.  Cleanup walks the tree again and
`os.remove`s every file (v0.2 has no `rmdir`, so empty dirs are
left behind — a documented v0.3 gap).

## Headline finding: v0.2 has no `os.mtime` / `pathlib.stat`

**This is the obvious P3b stdlib addition.**  The migration use
case "categorise files by age" is the canonical motivation for
file-metadata syscalls, and v0.2 doesn't expose any of them:

| Python API | StrictPy v0.2 status |
|---|---|
| `os.path.getmtime(p)` | **missing** |
| `os.path.getsize(p)` | **missing** |
| `os.stat(p).st_*` | **missing** |
| `pathlib.Path(p).stat()` | **missing** |

The workaround is to shell out — and the workaround is *fragile
in three ways at once*:

1. **Locale-dependent date format.**  On my Windows 11 host
   (regional settings: en-GB), `dir /T:W <path>` printed
   `19/05/2026  03:56 pm` (DD/MM/YYYY).  My first cut assumed
   en-US `MM/DD/YYYY` and trapped with
   `ValueError: month out of range (1..=12): 19` (the day was
   being parsed as the month).  The shipped code tries both
   orderings via `try ... except ValueError` — works on either
   locale but cannot disambiguate an ambiguous date (e.g.
   `03/05/2026` could be March 5th or May 3rd).
2. **Shell-quoting through `cmd.exe /c`.**  My first cut
   wrapped the path in `\"...\"` so spaces would be tolerated,
   and `dir` returned exit 1 with `"The system cannot find the
   path specified."`  cmd.exe re-parses the command-line and
   eats the inner double-quotes as the outer pair.  The shipped
   code omits quoting (and accepts that paths-with-spaces would
   break — a tradeoff the workaround can't avoid without a real
   `os.mtime`).
3. **`re.find_all` returns whole matches only.**  Python's
   regex returns Match objects with capture groups; M20c's
   `re.find_all` returns a flat `List[str]` of full matches
   (v0.2 spec §9.14).  I worked around by `re.find_all` on the
   whole `[0-9]{2}/[0-9]{2}/[0-9]{4}` and then `.split("/")` —
   ugly but workable.

**Fix sketch for P3b**: one new native `os.mtime(p) -> i64`
returning epoch seconds, plus the obvious `os.size(p) -> i64`
companion.  Rust's `std::fs::metadata(p)?.modified()?.duration_since(UNIX_EPOCH)?`
is ~5 lines per native, no new infrastructure.  Once landed,
`fs_migrator.spy` collapses from 340 LOC to ~120.

## Probe outcomes (10/10 reported, all PASS)

The numbered probes correspond to the in-program prints
(`probe<N>.<name>=PASS|FAIL`); the integration test asserts each
line is present in stdout.

| # | Probe | Outcome | Notes |
|---|---|---|---|
| 1 | Recursive `os.listdir` over 3 levels | **PASS** | Found all 5 files at depths 1, 2, 3.  No stack-limit issue — the v0.2 spec's 1024-frame bound (§14.2) is well above depth 3. |
| 2 | `pathlib.join` with mixed separators | **PASS** (with footgun) | `pathlib.join("foo/", "/bar")` → `"/bar"` (drops `foo/` because `/bar` is absolute — matches Python `os.path.join`).  `pathlib.join("foo", "bar/baz")` → `"foo\bar/baz"` on Windows (mixed `\` and `/` in one path).  Both behaviors match Python — but the second leaves an embedded `/` that `parts()` does NOT split on. |
| 3 | `pathlib.parts` round-trip | **PASS** | `parts(join(join("a","b"),"c.txt"))` → `["a","b","c.txt"]` (n=3). |
| 4 | `pathlib.stem` / `pathlib.suffix` edge cases | **PASS** | `archive.tar.gz` → `("archive.tar", ".gz")`; `README` → `("README", "")`; `.bashrc` → `(".bashrc", "")`.  All match the M20a spec and Python's convention. |
| 5 | `pathlib.with_suffix` on extensionless name | **PASS** | `with_suffix("notes.txt", ".bak")` and `with_suffix("notes", ".bak")` both produce `"notes.bak"`. |
| 6 | `pathlib.relative_to` happy + error path | **PASS** | `relative_to("a/b/c.txt", "a")` → child basename `"c.txt"`; `relative_to("x/y", "a/b")` raises `ValueError` (caught). |
| 7 | `datetime.diff_days` arithmetic | **PASS** | `from_ymd(2026,5,19) - from_ymd(2026,4,19) = 30` days; reverse direction = -30. Negative diffs return the correct sign (Python `//` floor-div, not truncation). |
| 8 | `subprocess.run` for `stat`/`dir` mtime | **PASS** (after locale-fix) | Required the DD/MM-vs-MM/DD try/except workaround described above. |
| 9 | `pathlib.read_text` UTF-8 round-trip | **PASS** | A 27-char string mixing Greek (α/β/γ), em-dash, and Han (中文) round-tripped via `write_text` + `read_text` byte-for-byte.  `len(got) == 27` (the StrictPy `len()` returns codepoint count). |
| 10 | `os.mkdir` + `os.remove` + `os.is_dir` dance | **PASS** | `mkdir(d)` succeeds; `is_dir(d)` returns true; `write_text(d/victim.txt)` + `os.remove` + `is_file` returns false.  **Caveat**: v0.2 has no `os.rmdir`, so the test subdir is leaked — see "v0.2 gaps" below. |

## Cross-platform notes

* **Windows `dir` output is locale-dependent.**  My host (en-GB)
  gave DD/MM/YYYY; en-US would give MM/DD/YYYY; some Asian
  locales use YYYY-MM-DD.  The try/except disambiguation works
  for unambiguous dates but cannot tell `03/05/2026` apart.  A
  real `os.mtime` would sidestep this entirely.
* **`cmd.exe /c` re-parses the second argument** in a way that
  eats nested double-quotes.  The shipped code skips path
  quoting (no-spaces assumption).  A more robust workaround
  would build the argv list with the path as a *separate*
  argument and rely on Rust's `Command::args` quoting — but
  `dir` is a cmd.exe builtin, so it must be passed as a single
  command string.
* **Path separators on the join output.**  `pathlib.join("foo",
  "bar/baz")` produces `"foo\bar/baz"` on Windows — the join
  inserts `\` but doesn't normalise the embedded `/`.  This
  flows through to `parts()`, which only splits on `\` on
  Windows, leaving `bar/baz` as a single component.  The fix
  belongs in v0.3 (a `pathlib.normalise` or
  `Path.resolve`-style cleanup).
* **`os.remove` on a directory** raises IOError (correct
  Unix-like behaviour).  The migrator's cleanup loop walks
  files-only, so this never trips — but a future v0.3 `os.rmdir`
  primitive is the natural pair.

## v0.2 gaps surfaced (in priority order for P3b)

1. **`os.mtime(p) -> i64` / `os.size(p) -> i64`.**  As above —
   the headline finding.  No metadata access in v0.2 forces the
   subprocess workaround.  ~10 LOC each in `vm/src/builtins.rs`,
   no new infrastructure.
2. **`os.rmdir(p) -> None`.**  Spec §9.7 lists `os.mkdir` but
   not `os.rmdir`; without it cleanup leaves empty directories.
   ~5 LOC.
3. **`re.find_all` returning match objects (or a paired
   `re.find_all_groups`).**  Capture groups are listed as v0.3
   work in §9.14 — but the simpler "give me the whole match
   AND the capture groups" form would unblock most parsing
   workarounds.
4. **`pathlib.normalise(p)` / `Path.resolve()`.**  Embedded
   forward slashes on Windows + the `parts()` non-split is the
   minor surprise.  v0.3 stdlib classes will land `Path.resolve`
   anyway.
5. **`subprocess` env-var injection.**  Not exercised in this
   program, but the spec §9.24 already flags it as v0.3.  Worth
   noting that running `dir` with a non-default locale via
   `env={"LANG": "C"}` would have sidestepped probe 8's
   locale-fragility in one line.

## What worked clean

The M23 P3a-A pathlib API is *very* close to Python's flat
function shape and absorbed everything I threw at it.  The
multi-extension `stem`/`suffix` cases (probe 4) all match Python
exactly; `relative_to` raises `ValueError` (not `RuntimeError`
or `IOError`) per the spec, which made the try/except clean.

The M23 P3a-B `datetime` module:
* `from_ymd` validation surfaced the locale bug (probe 8) cleanly
  as a catchable `ValueError`.  This is the right error class
  per Python convention.
* `diff_days` over a small range was exact (probe 7); the floor
  semantic for negative diffs matched the spec.

The M23 P3a-A `subprocess.run` 3-tuple shape was easy to consume
(`r.0` exit, `r.1` stdout, `r.2` stderr) — no surprises.

M20a's `os.listdir` + `os.mkdir` + `os.remove` + `os.is_dir` +
`os.is_file` all worked first try; the recursive walker (probe 1)
is a ~10 LOC function with no infrastructure gymnastics.

M20a's `io` was implicitly exercised through `println` for the
report output — no direct `io.input` use was needed for this
program.

## Honesty: what was hard, what I didn't try

* I did NOT exercise the *future*-mtime / clock-skew probe
  (the brief listed "diff_days when mtime is in the future" as
  a likely bug shape).  The subprocess workaround makes
  injecting a future mtime ugly (you'd need to `os.set_env`
  some library var, or shell-out to `touch -d "+1 day"`).  Once
  P3b ships `os.mtime`, this probe collapses to two lines and
  should be a unit test.
* I did NOT push recursion depth to the 1024-frame limit.  Probe
  1's tree is 3 deep.  The brief flagged a deep-listdir probe
  as interesting; reaching 1024 would require ~500 nested
  `os.mkdir` calls in setup — feasible but the time budget said
  to stop here.  A future stress test can do this in isolation.
* I did NOT try the embedded-`\0` case mentioned in the brief
  for read_text.  `pathlib.write_text` would happily write a
  `\0`-containing string, but `os.write_file`'s path handling
  on Windows treats `\0` as end-of-string at the FFI boundary —
  not really a v0.2 stdlib bug, more an OS quirk.
