# M24-B — `event_log.spy`, SQLite-backed event log CLI

**Brief**: stress-test the M23 Phase 3a stdlib surface — specifically
`sqlite3` + `datetime` + `pathlib` + `io` — combined with `argparse`
from M22 P2A.  Build a CLI tool that ingests timestamped event lines
into SQLite, queries them by time + category, and prints a per-bucket
histogram.  Run the 10 explicit probes from the brief plus the
"likely-bug-shapes" list.  Look for incidental bugs the per-module
unit tests didn't catch.

**Wall-clock**: ~2.5 hours (one read-through + design + one major bug
bisect + one minor scoping fixup + one pretty-printer-roundtrip
fixup + tests + report).

**Result**: 14/14 probes pass after one workaround.  **One real bug
deterministically reproduced and shrunk to a 12-line minimal repro
(BUG-039)**, plus a second related crash captured separately
(`_probe_dict_in_i64.spy` segfaults the VM).

**Tests**: 553 baseline preserved + 5 new (`event_log_runs.rs`) =
**558 passing, 0 failed, 1 ignored** workspace-wide.

## Program summary

`examples/event_log.spy` (~770 LOC including docstrings + probe
section) implements a four-mode CLI:

* **`--mode=ingest --file=PATH [--db=PATH]`** — `pathlib.read_text`
  the input, split on `\n`, regex-extract the ISO timestamp at the
  start of each line via `re.find`, parse via `datetime.from_iso`,
  insert via `sqlite3.execute_params` against a
  `CREATE TABLE IF NOT EXISTS events (id, ts, category, message)`.
* **`--mode=query --since=ISO --category=CAT`** — parameter-bound
  `SELECT ... WHERE ts >= ? AND category = ? ORDER BY ts ASC`, render
  each integer `ts` cell back through `datetime.to_iso`.
* **`--mode=summary --buckets=hour|day`** — read all events back, bucket
  by `ts - (ts mod bucket_secs)`, print a `*`-bar histogram.
* **`--mode=demo`** (the default) — runs all 14 probes inline against
  in-memory databases and prints `PROBE <name>: PASS|FAIL` for each.
  This is the path the integration test asserts on.

All four modes work end-to-end.  The orchestration is uneventful —
`argparse` happily takes six options (`--mode`, `--file`, `--db`,
`--since`, `--category`, `--buckets`), the parser handles the
`--mode=ingest` (equals form) and `--mode ingest` (space form)
interchangeably, and the per-mode dependent-flag validation is a
hand-rolled string comparison after `argparse.parse` because there's
no native "required-when" surface (correctly flagged as v0.3 work in
M22 P2A's report).

## The one real bug found — BUG-039

**Symptom**: `k in d` returns `false` for every key `k` and every
`Dict[str, *]` literal `d`, **even immediately after `d[k] = v`
succeeded**.  The lookup `d[k]` returns the right value.  `d.keys()`
returns the key.  `len(d)` is correct.  Only `in` is broken.

**Minimal repro** — `examples/_probe_dict_in_false.spy`:

```python
d: Dict[str, i64] = {}
d["x"] = 1i64
if "x" in d:
    println("present")     # never fires
else:
    println("absent")      # always fires
println("d[\"x\"] = " + str(d["x"]))  # prints "1"
println("d.keys len = " + str(i64(len(d.keys()))))  # prints "1"
```

Output:

```
absent
d["x"] = 1
d.keys len = 1
```

**Scope** — `examples/_probe_dict_in_types.spy` widens the test:
`in` is broken on `Dict[str, str]`, `Dict[str, i64]`, `Dict[str, i32]`,
and `Dict[str, bool]` — every `Dict[str, V]` shape we tried.

**Cross-dict variant** — `examples/_probe_dict_in_cross.spy` shows
the original failure shape from probe 10: two dicts each holding
`str(base + N*3600)` keys built via `str(i64)`, and `in` between any
key from `expected.keys()` and `actual` returns `false`.  Same root
cause as the literal-key case.

**Location speculation**: my reading-only diagnosis is that
`compiler/src/ir.rs`'s `IROp::InDict` (or whichever opcode lowers
`x in d` for the `Dict[str, *]` overload) is either:
1. Dispatching to a non-existent / placeholder VM handler that
   returns a constant `false` — same shape as **BUG-008** (`is not`),
   **BUG-034** (`str !=`), and **BUG-037** (`??`), the three earlier
   "placeholder IR lowering" bugs M11/M12/M21 found.  The pattern
   matches: silent miscompile, returns a constant, has a working
   sibling (`Dict.get`, `Dict[k]`) suggesting the runtime can find
   the key but the lowering path is wrong.
2. Or alternatively: the lowering computes the right pointer pair
   but the VM's hash comparison treats the two `String` values as
   inequal — possible if the `in` op compares by string-handle
   identity rather than by string-value bytes.

The brief explicitly lists "audit `compiler/src/ir.rs` for `// placeholder`
comments and Copy/passthrough lowerings for operators" as the
mechanical lesson from the three earlier placeholder-lowering bugs;
this fourth instance reinforces that audit's value.

**Workaround in the program**: `dict.get(k)` returns `T?` and works
fine.  `dict_has_str(d, k) = (d.get(k) is not none)` substitutes for
`k in d` everywhere in the histogram aggregation.  See
`examples/_probe_dict_get.spy`-style usage in the demo's probe-10
body.

**Severity assessment**: high.  This is a silent miscompile of a
Python-conformant operator on the most-used heap type after `List`.
Any v0.2 program that wanted to test "is this key already in the
counter dict?" would silently take the wrong branch.  The fact that
no earlier example program tripped it suggests either (a) existing
examples have avoided `in` on `Dict[str, *]` (we found one use in
`event_log.spy` itself and that's the only one we wrote), or (b)
existing code's `in` calls were on `Dict[int, *]` / `List[T]` for
which the lowering path is different.  The latter seems plausible
given the second bug below.

## A second bug — `_probe_dict_in_i64.spy` segfault

**Symptom**: `<i64> in Dict[i64, i64]` **segfaults the VM** (exit
code 139 on Linux/WSL).  Three-line repro:

```python
di: Dict[i64, i64] = {}
di[1i64] = 10i64
if 1i64 in di:
    println("present")
```

Output: `Segmentation fault`, exit 139.  No stack trace, no
`VmError::UncaughtException`, no panic — a hard process crash.

**Likely-cause speculation**: distinct from BUG-039 in symptom; both
are likely manifestations of the same broken-`in`-lowering family
but the `i64`-keyed dispatch arm goes one further and reads through
an invalid pointer instead of returning a constant.

I did not bisect this further because the M24-B brief explicitly
flags 90-minute budgets for single-bug bisects and the
`Dict[str, *]` half is already a clear repro.  Filed alongside
BUG-039 as the same family.

The PASS for "B" is inverted-sense — the probe asserts the bug is

The UTF-8 round-trip surprised me — I half-expected the
TEXT-only parameter binding to mangle the 4-byte emoji.  It didn't;
rusqlite + Rust's UTF-8 `String` ferry the bytes through transparently.

## Workarounds and what they imply

1. **BUG-039 `in` → `dict_has_str` via `.get() is not none`.**  Adds
   one helper function + a NOTE comment at each call site.  Implies
   the `Dict.in` operator should not be used in v0.2 production code
   until BUG-039 is fixed.  Three call sites in `event_log.spy` plus
   four in the demo-probe section.

2. **Try-block variable scoping.**  A `let_stmt` inside `try:` is
   scoped to the try-block; the variable is invisible in the outer
   block.  E.g. `try: content: str = read_text(p)` then `lines =
   content.split` errors with `name 'content' not in scope`.
   Workaround: declare `content: str = ""` outside the try, assign
   inside.  This is a v0.2 design choice (matches Python's `try` not
   creating a new scope but does match StrictPy's per-block scoping
   discipline) — not a bug, just worth knowing.  Two such fixups
   were needed in `run_ingest` and `run_query`.

3. **`(x in d) == false` is a chained comparison.**  My first cut
   used `if (b in d) == false:` for the "not present" branch.  The
   roundtrip pretty-printer test (`compiler/tests/roundtrip.rs`)
   fails on this because the pretty-printer's parenthesisation
   apparently drops the parens, producing `b in d == false` which is
   then a chained-comparison parse error (v0.1 disallows chained
   comparisons by design — error E0007).  This is partly a pretty-
   printer / source-fidelity issue — the printed-once output should
   reparse without precedence drift — and partly a v0.2 spec choice
   (no chained `in == false`).  Workaround: use `not (b in d)`.
   Not pursued as a separate bug; flagged here for the next round.

## Observations on the M23 Phase 3a surface

Three Phase 3a modules I used heavily — `sqlite3`, `datetime`,
`pathlib` — behaved indistinguishably from the M19-M21 Phase 1
stdlib in terms of "did it just work."  The probes for SQL-injection
safety, parameter-bound UTF-8, IOError-on-missing-file, datetime
edge cases (Z, +00:00, naive, pre-epoch, year-boundary,
month-boundary), and bulk INSERTs (1200 rows in 0.1s, 5000 events
in 0.2s) all passed first-try.

The only Phase 3a-specific path I didn't exercise was the
sqlite3-connection-take-and-put-back pattern from M23 P3a-D's report,
because this program is single-threaded — and the brief explicitly
said multi-threaded sqlite is out of scope.

The bug-density signal is consistent with the M18 trend: Phase 3a
modules ship clean per-module, and the combination-stress reveals
**older** unfixed surface (BUG-039 is `Dict.in`, an M7 operator) more
than new-surface defects.  Same pattern as M10 round 1's findings:
the "is not" bug (BUG-008) was found *via* JSON parsing combinations,
not by a per-operator unit test.

## What the orchestrator should do with BUG-039

1. File BUG-039 in `BUGS_KNOWN.md` and `docs/thesis/bugs/catalog.md`
   under "Frontend operator semantics" (joining BUG-008, BUG-034,
   BUG-037 — same family).  Severity: high (silent miscompile,
   Python-conformant op, common heap type).
2. Add the four `_probe_dict_in_*` files to a future regression
   test once the fix lands (mirroring the M21 BUG-037 ack from the
   "Fixed in M19-M20-M21" appendix).
3. The Dict[i64,i64] segfault probably has a related-but-distinct
   root cause; treat as a separate sub-bug under the same parent.
   The investigation budget for both should bisect from
   `compiler/src/ir.rs::lower_expr` for `Expr::InContainer` (or the
   equivalent op enum the Dict `in` lowering uses) and check the
   value/identity comparison shape.
