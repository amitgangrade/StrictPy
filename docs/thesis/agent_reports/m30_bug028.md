# M30 — BUG-028 (lexer line continuation across trailing infix operators)

## Summary

Closed the **last legacy frontend bug** in StrictPy. The lexer now
suppresses the synthetic `Newline` token when the last significant
token is a binary operator that requires a right-hand operand — the
same way it already suppresses `Newline` inside `()`/`[]`/`{}` via
paren-counting. The canonical repro

```python
fn make_msg() -> str:
    return "a " +
        "b"
```

now compiles and prints `a b` (previously: `E0001: expected newline,
found ...`).

Bug totals: 35 found, 33 → 34 fixed, 2 → 1 deferred. The deferred item
is the stdlib network/concurrency carve-out, not a language bug; the
**legacy frontend backlog is now empty**.

## Where the bug lived

`compiler/src/lexer.rs`. The newline branch around line 249 only
suppressed `Newline` when `paren_depth > 0`. There was no notion of
"the last token was infix and needs a RHS"; once the lexer saw `\n`
outside parens it emitted `Newline` unconditionally, and the parser
then saw the start of the continuation line as a statement.

The closing-paren rule trivially handled `("a " + \n "b")`, which is
why the workaround the M10–M24 agents reached for was always either
wrapping in parens or accumulator-style string building. BUG-028 was
catalogued at M10 and deferred for 12 milestones because every program
had two clean workarounds.

## Fix shape

Three changes in `compiler/src/lexer.rs`, all additive:

1. **New field** `last_significant_kind: Option<TokenKind>` on `Lexer`.
2. **`next_token`** now updates this field after every non-`Indent` /
   non-`Dedent` / non-`Newline` / non-`Eof` token. Cloning a `TokenKind`
   is cheap (most variants are unit; the only allocating one is
   `Ident(String)`, which is irrelevant here because no `Ident` triggers
   continuation).
3. **New predicate** `last_token_continues_line()` returns true iff the
   last significant token is one of the operators/keywords that demand
   a right operand: arithmetic (`+ - * / // % **`), assignment
   (`= += -= *= /= //= %= **= &= |= ^= <<= >>=`), comparison
   (`== != < > <= >=`), boolean (`and`/`or`), bitwise
   (`& | ^ << >>`), membership/cast keywords (`in`/`is`/`as`), and
   `??`.
4. **`next_token_inner`** — in the `paren_depth == 0` branch of the
   newline-emit path, check the predicate. If true, recurse into
   `next_token_inner()` (the same call the `paren_depth > 0` branch
   already does to swallow whitespace) instead of emitting `Newline`.

The continuation line's leading indentation is consumed naturally:
`at_line_start` stays `false`, so `handle_line_start` is NOT invoked,
and `skip_inline_whitespace` eats the spaces just as it would on any
other inline whitespace. No `INDENT`/`DEDENT` is emitted for the
continuation line — by design, mirroring the paren rule.

## What did NOT trigger continuation

Deliberately omitted from the predicate:

- **`Colon`** — block headers like `if x:` MUST end the logical line so
  the `INDENT` of the body comes next.
- **`Comma`** — the only places `Comma` appears unparen'd are tuple
  unpack targets at statement level, which never end a line.
- **`Dot`** — `obj.method` rarely spans lines and is awkward to read
  continuation-wrapped.
- **`Arrow`, `At`, unary `Not`/`Tilde`** — niche or unary; conservative
  to skip.

This conservative set matches the "binary operator requiring a RHS"
intuition. If a future agent finds a real-world ergonomics gap (e.g.
trailing `.` for method chains), it's a 1-line addition.

## Spec amendment

`STRICTPY_SPEC.md` §3.2 (Line structure) gained one bullet documenting
the new rule and enumerating the trigger set explicitly, plus the
note that `:`, `.`, `,`, `->`, `@`, unary `not`/`~` do NOT trigger.
The existing physical-line-continuation (`\\\n`) and paren-counting
bullets are unchanged.

## Methodology note

This was a deliberately small task (~75 minutes wall-clock). The
implementation is ~95 lines of additive code in one file, plus a
spec bullet and a test file. No IR / typecheck / codegen / VM touched.

The interesting design call was the trigger set. Python's reference
implementation does NOT do operator-trailing continuation (you'd get a
`SyntaxError`); both Python's PEP 8 and `black` recommend wrapping in
parens. The task brief overstates Python's behaviour, but the StrictPy
extension is independently sensible — it's exactly the ergonomic gap
that drove M10's BUG-028 catalogue entry. The conservative trigger set
guarantees zero false-positive line-joins (every trigger is a token
that's syntactically incomplete without a RHS, so the line was already
going to error if the next line wasn't a continuation).
