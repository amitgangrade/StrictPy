# M22 P2B — `base64` / `hashlib` stdlib modules

**Brief**: Ship the two smallest Phase-2 stdlib modules on top of the
M19 stdlib-module-table infrastructure: standard + URL-safe base64
codecs (`base64`) and md5/sha1/sha256/sha512/HMAC-SHA256 digests
(`hashlib`). Both are pure-Rust crate wrappers; the diff per module is
a `seed_stdlib_modules` entry plus a handful of `NativeFn` handlers.

**Wall-clock**: ~1.5 hours (read-through of SHARED_BRIEF + the M19,
M20a, M20c reports; 9 native handlers totalling ~110 LOC; 16
in-process tests + 4 subprocess tests + 2 example programs + spec
update).
**Files changed**: 5 source files + 5 cargo deps + 1 spec section
(§9.15 + §9.16) + 1 agent report + 2 new examples + 3 new test files.
**Tests**: existing M21 baseline + **20 new** (16 in-process + 4
subprocess across two example programs) — all green locally.

## Strategy: crate-wrap each algorithm

The brief explicitly recommended crates over hand-rolling for base64
("it's ~80 LOC of lookup table — recommend the crate"), and the
hashlib case is even stronger (SHA-2's compression function is ~500
LOC of bit-bashing on top of a vetted FIPS 180-4 test suite that
RustCrypto already passes). I added five tiny crates to `vm/Cargo.toml`:

```toml
base64 = "0.22"
md-5   = "0.10"
sha1   = "0.10"
sha2   = "0.10"
hmac   = "0.12"
```

The `base64` crate's 0.22 series exposes a stable engine API; I use
`base64::engine::general_purpose::STANDARD` (RFC 4648 §4, `+`/`/`,
`=`-padded) and `URL_SAFE_NO_PAD` (RFC 4648 §5, `-`/`_`, no padding).
The RustCrypto hash crates all expose the same `Digest` trait
(`new() → update() → finalize()`), so the four hash handlers are
near-identical four-line bodies; the `hmac` crate composes on top via
`Hmac<Sha256>`.

I went one rung past the brief's stretch goal and shipped
`hashlib.hmac_sha256` — it's a 10-line handler and it's the workhorse
of every API-signature / JWT / cookie-tamper-detection use case real
StrictPy programs would want this module for. The brief said "ship
without it if it's a significant lift", but it was four lines on top
of the SHA-256 wiring.

## NativeFn ID layout — full 290–309 range available, used 290–304

| Range  | Module    | Count | Notes |
|--------|-----------|-------|-------|
| 290–293 | `base64`  | 4 | encode / decode / encode_url_safe / decode_url_safe |
| 300–304 | `hashlib` | 5 | md5 / sha1 / sha256 / sha512 / hmac_sha256 |

294–299 are reserved for v0.3 `base64.encode_bytes` / `decode_bytes`
and the b32/b16 family if/when they ship. 305–309 are reserved for
SHA-3, BLAKE2/3, and a streaming-hasher class handle (which needs
stdlib-class-registration infrastructure that's still v0.3 work).

## Cross-platform notes

Both modules are pure-Rust and depend on zero OS surface (no
`std::env`, no `std::fs`, no `std::time`). All five crates compile
cleanly on Windows + Linux + macOS without `cfg(target_os = ...)`
gates. The only cross-platform-relevant detail is line-ending
handling, which doesn't apply here — base64 strings carry no
newlines (we don't emit MIME-style 76-char wrapping) and hex digests
are pure ASCII.

The known-vector tests pass identical hex strings on Windows where I
developed and Linux CI — no platform-conditional assertions needed.

## Strings carry UTF-8 — the `bytes` round-trip story

StrictPy v0.2's `str` carries UTF-8; v0.2's `bytes` is a legacy
prelude alias for `str` with no first-class byte-buffer API. This
forced a design call for `base64.decode`: the natural shape
(`b64 → bytes`) doesn't fit, and I had two choices:

1. **Skip `decode` entirely** — defer the whole module to v0.3 when
   `bytes` exists.
2. **`decode` returns `str` after a UTF-8 check** — works for the
   common case of round-tripping text payloads (tokens, small config
   blobs); raises `ValueError` for binary payloads.

I picked (2). It loses generality for binary blobs but gains the
ergonomic case ("encode this access token for the URL"). The spec
amendment (§9.15) explicitly documents the limitation and points at
v0.3 for `encode_bytes` / `decode_bytes`. The example
`base64_demo.spy` exercises the UTF-8 path with a multi-byte payload
(the euro sign, 3 bytes in UTF-8) to make sure we don't lose bytes
along the way.

`hashlib` has the same shape with no real downside: hash inputs are
UTF-8 bytes derived from a `str`, and outputs are always lowercase
hex (always ASCII). Programs that need to hash binary data have to
wait for v0.3, but the typical "hash this string" use case lands
cleanly.

## Known-vector validation

All four hash algorithms are validated against published vectors in
both the in-process test (`vm/tests/m22_p2b_base64_hashlib.rs`) and
the example program (`examples/hashlib_demo.spy`):

* `md5("") = d41d8cd98f00b204e9800998ecf8427e` (RFC 1321 §A.5)
* `md5("The quick brown fox jumps over the lazy dog") = 9e107d9d372bb6826bd81d3542a419d6`
* `sha1("") = da39a3ee5e6b4b0d3255bfef95601890afd80709`
* `sha1("abc") = a9993e364706816aba3e25717850c26c9cd0d89d` (FIPS 180-4 §A.1)
* `sha256("") = e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`
* `sha256("abc") = ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad` (FIPS 180-4 §B.1)
* `sha512("abc") = ddaf35a193617abacc417349ae20413112e6fa4e89a97ea20a9eeee64b55d39a2192992a274fc1a836ba3c23a3feebbd454d4423643ce80e2a9ac94fa54ca49f` (FIPS 180-4 §C.1)
* `hmac_sha256("key", "The quick brown fox jumps over the lazy dog") = f7bc83f430538424b13298e6aa6fb143ef4d59a14946175997479dbc2d1a3cd8` (verified against Python's `hmac.new(b'key', ..., hashlib.sha256).hexdigest()`)

base64 vectors come from RFC 4648 §10 (`"Man" → "TWFu"`) plus a
custom multi-byte-UTF-8 case and a URL-safe-vs-standard alphabet
case that asserts encoding `"??>>"` produces standard `Pz8+Pg==`
but URL-safe `Pz8-Pg` (replacing `+` with `-` and dropping padding).

## Hardest three things (in retrospect)

1. **The `bytes`-shaped hole for `base64.decode`.** Took the most
   thinking time — not the implementation, the API design call.
   The right answer for v0.3 is clearly `decode(b64) -> bytes`, but
   v0.2 has no usable `bytes` surface, and `decode → str` is the
   most-common use case. Documenting the limitation prominently in
   §9.15 felt better than skipping the function entirely.

2. **Picking the `base64` engine constants.** The 0.22 series moved
   to a builder-style engine API (`GeneralPurpose::new(alphabet,
   config)`) but exposes pre-built `STANDARD` / `URL_SAFE_NO_PAD` /
   `STANDARD_NO_PAD` / `URL_SAFE` constants under
   `engine::general_purpose`. The brief's spec says URL-safe should
   have **no padding** ("URL-safe variant ... no padding"), so I
   used `URL_SAFE_NO_PAD` rather than the also-existing `URL_SAFE`.
   This is also what JWT / OAuth code expects, so it lines up with
   real-world programs that import this module.

3. **Verifying the HMAC-SHA256 known vector matches Python.** The
   regular hash vectors are well-published (NIST FIPS 180-4); the
   HMAC vectors in RFC 4231 use binary keys (e.g. `0x0b * 20`) that
   don't map cleanly to a `str`-keyed surface. I picked a simple
   ASCII-key vector and verified it locally against `python3 -c
   "import hmac, hashlib; print(hmac.new(b'key',
   b'The quick brown fox jumps over the lazy dog',
   hashlib.sha256).hexdigest())"` before pinning it in the test.
   The hex matched on first try — RustCrypto's `hmac` is the same
   bit-exact construction Python uses.

## Incidentally-discovered bugs / oddities

* **None requiring code changes.** Adding two crate-wrap modules
  flowed through the M19/M20 infrastructure without any
  resolver/typecheck/IR tweaks — five cargo deps and two
  `seed_stdlib_modules` entries were the entire diff outside the
  per-handler dispatch arms. This is the second consecutive M2x
  sub-milestone with no incidental-bug discovery (M20c also reported
  zero), which I read as a maturity signal: the
  stdlib-module-table seam is now wide enough that pure
  crate-wrapper modules are mechanical.
* No `match` keyword collisions (the M20c hazard) because neither
  `base64.encode`/`decode` nor any `hashlib.*` entry point uses a
  reserved word as an attribute name.
* The brief's stretch HMAC item turned out to be smaller than
  shipping it as a deferred bullet would have been — it slots in as
  one match arm and reuses the SHA-256 wiring.

## Cross-platform notes

Both modules are 100% pure-Rust and platform-agnostic. All five new
crates compile on Windows, Linux, and macOS without `cfg(target_os)`
gates. The hex digests are ASCII-only; the base64 alphabet is ASCII
in both standard and URL-safe modes. No line-ending normalisation
applies — we don't emit MIME-wrapped output. The in-process tests
pass identical hex bytes on Windows where I ran them and should pass
unchanged on Linux/macOS CI bots.

## What's next (v0.3 / Phase 3 candidates)

* **`bytes` round-trip for base64.** Add
  `base64.encode_bytes(data: bytes) -> str` and
  `base64.decode_bytes(b64: str) -> bytes` once the language gets a
  real `bytes` surface (indexable `u8` buffer with its own `len`,
  slicing, etc.). The native handlers are trivial; the work is in
  the language, not the stdlib module.
* **Streaming hasher handle.** `hashlib.new(algo: str) -> Hasher`
  with `Hasher.update(data: str)` and `Hasher.hexdigest()` methods.
  Same blocker the typed-`JsonValue` tree hit in M20c — needs
  stdlib-class registration through `StdlibModule`, currently held
  back until at least one user program actually wants it.
* **More algorithms.** SHA-3 (Keccak), BLAKE2/BLAKE3, RIPEMD-160.
  Each is one crate plus one handler; held back until a real-world
  example program asks for them.
* **`pbkdf2_hmac` / `scrypt` / `argon2`.** Password-hashing primitives
  — they need bytes-as-output (or hex-of-bytes), and the typical
  user wants a higher-level password-store wrapper anyway.
* **MIME-style line wrapping for base64.** RFC 2045 §6.8 calls for
  76-char lines for legacy email transport; ship if any real-world
  example program needs it. Trivial wrapper over the current
  handlers.

P2B was the fastest of the four Phase-2 stdlib agents the SHARED_BRIEF
predicted, exactly because both modules are pure crate-wrap. The
heavy lifting was deciding the `bytes`-shaped API gap (option 2 with
clearly-documented limitation) and verifying every published test
vector — both one-shot calls.
