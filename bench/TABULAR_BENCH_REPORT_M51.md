# StrictPy `tabular` vs pandas 3.0 — M51 merge codes-hash bench

_Generated by `python bench/tabular_harness.py --ops merge_str,merge_cat_via_strings,merge_cat_codes --sizes medium,medium_card_5000`.  Best of 1-3 runs per cell.  Wall-clock for execution of pre-compiled bytecode._

- **StrictPy**: post-M51 release build (`cargo build --workspace --release`).  M51 adds the `merge_cat_codes` bench cell that exercises the M49 merge codes-hash fast path on a categorical key (both frames keyed on a `col_categorical_ordered` column with bit-identical `categories[]`).
- **pandas**: 3.0.0 / numpy 2.4.6 on Python 3.x.
- **Host**: Windows 11, single-thread workload.
- **Memory measurement**: psutil RSS polled every 50 ms.
- **Run**: `iters=1` (best-of-1) for these heavy merge cells; `medium` =
  10,000 rows, `medium_card_5000` = 10,000 rows over 5,000 distinct keys.

## Headline: M49 merge codes-hash fast path (measured via M51 cell)

The M49 `merge` codes-hash fast path triggers when both frames key on a
`ColumnCategorical` with identical `categories[]` orderings: the join
hashes the i64 codes instead of coercing to strings.  M48's
`merge_cat_via_strings` cell merged two `astype("category")` frames on
pandas but plain str frames on StrictPy — it never exercised the codes
path.  `merge_cat_codes` closes that gap.

## What the numbers show

- **The codes-hash path eliminates the string-coercion catastrophe.** On
  `medium` (low cardinality → a large many-to-many cross-product), the
  same merge is **1,425 ms via codes vs 124,922 ms via string coercion —
  an ~88× speedup**, and it beats pandas (4,941 ms) at **0.29× (3.4×
  faster)**.  This is the headline M49 win the M48 suite never captured.
- **Low cardinality is where codes win biggest.** The cross-product blows
  up both runtime and memory on the string path (9.3 GB RSS, 125 s); the
  codes hash collapses the key comparison to an i64 hash, so StrictPy
  finishes in 1.4 s at 1/9th the RSS.
- **High cardinality is the remaining gap.** At 5,000 distinct keys
  (~2 rows/key → a small join result), `merge_cat_codes` runs **5.93×
  slower than pandas** (23,809 vs 4,014 ms) — though at **0.23× the RSS**
  (21 MB vs 90 MB).  StrictPy trades memory for time here; the per-row
  join bookkeeping dominates when there's no cross-product to amortize it.
  Flagged as a future optimization target (the merge inner loop, not the
  codes hash itself).

## Methodology notes

- `merge_cat_codes` builds the categorical key on both StrictPy frames
  via `tabular.col_categorical_ordered(values, cats)`, with `cats`
  derived by a first-appearance dedup of the (null-filled) category
  column so both frames share a bit-identical `categories[]` list — the
  precondition for the M49 codes-hash path.  The pandas comparand casts
  the key to a fixed-ordering `pd.CategoricalDtype` before merging.
- All other M48/M49 cells are unchanged by M51.
- Running the harness rewrites `bench/TABULAR_BENCH_REPORT.md` (the M48
  aggregate report) — that file was restored to its committed M48 state
  after this M51 subset run; only this M51 report carries the merge
  numbers above.

## Open caveats

- `large` (1M-row) cells still skip per the M48/M49 cut decision.
- The high-cardinality `merge_cat_codes` slowdown (5.93×) is the clearest
  open perf item for a future milestone; the low-cardinality win confirms
  the codes-hash design is sound.
